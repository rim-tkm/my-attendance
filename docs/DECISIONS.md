# DECISIONS — 意思決定ログ（ADR-lite）

> **新しい判断をしたら末尾に追記すること**（消さない）。フォーマット: 日付 / 決定 / 背景 / 選択肢 / 理由 / 影響。

## ADR-001: データは Supabase を直接（ORMなし）
- **決定**: `@supabase/supabase-js` を直接使い、ORMは導入しない。
- **理由**: 小〜中規模で構造が単純。ORMの学習/保守コストを避ける。`lib/supabase-data.ts` に集約して境界を保つ。
- **影響**: SQL/クエリは `lib/supabase-data.ts` に集中。DBカラム変更時は `to*` マッピングも直す必要。

## ADR-002: 画面は単一巨大ファイル `app/page.tsx`
- **決定**: 管理画面・メンバー画面を1つの client component に内包（`AdminDashboard` を `DashboardPage` が内包）。
- **背景**: 段階的に育った結果、約10,700行。
- **理由（現状維持の）**: 分割は大工事でリスクがある。既存の `adminSection` state による切替が機能している。
- **影響/負債**: 保守が重い。**新規機能はできるだけ `lib/` にロジックを出し、将来のコンポーネント抽出に備える**。分割は独立タスクとして計画的に。

## ADR-003: 管理番号は単純連番（登録日は保持しない）
- **決定**: `invoice_number` は `max+1` の連番。`users.created_at` は追加しない（当面）。
- **背景**: 登録日カラムが無く、後付けしても既存メンバーは全員「追加時刻」になり無意味。
- **理由**: 連番は「登録の新しい/古い」の順序は表せる。休眠/未稼働の判別には順序で十分。
- **影響**: 「本当の新人 vs 昔登録して未稼働」を日付で自動判別はできない。未稼働一覧は管理番号降順で緩和。将来 created_at を足すなら「追加後の新規のみ正確」と割り切る。

## ADR-004: 休眠を「休眠」と「未稼働」に分離
- **決定**: 在籍・時給制・非インターンを、①休眠（過去に打刻歴あり・直近3ヶ月なし）②未稼働（一度も打刻なし・新人含む）に分ける。
- **背景**: 「3ヶ月打刻なし」だけだと新規加入直後の人が休眠に誤検出される。
- **理由**: 登録日が無い中で唯一確実な判別軸は「過去に打刻歴があるか」。歴があれば新人ではない。
- **影響**: 休眠カウントに新人が混ざらない。未稼働の一括無効化は新人混在リスクありのため注意書き＋管理番号降順。

## ADR-005: 一括無効化は既存の単体無効化を流用
- **決定**: 休眠/未稼働の一括無効化は `updateMember(id,{isActive:false})` を選択分ループ。
- **理由**: 既存の単体無効化と完全に同経路＝安全・可逆（アーカイブ復元可）。独自実装でロジックがズレるのを避ける。
- **影響**: 破壊的操作なので確認ダイアログで対象氏名を明示必須。

## ADR-006: パフォーマンス改善をフェーズ分け
- **決定**: フェーズ1（初回二重ロード解消＋SELECT列限定）を先に実施。フェーズ2（表示ロードの期間制限A／サーバー集計D／page分割E）は別途設計。
- **理由**: フェーズ1は「クライアントが受け取るデータの中身を変えない」低リスク改善。フェーズ2は履歴系画面（請求/CSV/予実乖離/カスタム集計）の動作確認が要る。
- **影響**: 現状はフェーズ1のみ完了。重さ再燃時はフェーズ2-Aを最優先で設計着手。

## ADR-007: 率(%)の2桁表示は「丸めずに再計算」
- **決定**: 2桁精度が要る所は `safeRatePercent`(1桁丸め) ではなく `ratePercent2`(`Math.round(x*10000)/100`) を使う。
- **背景**: 既存の率計算が1桁丸め。表示だけ `.toFixed(2)` にしても末尾ゼロになるだけ。
- **影響**: `lib/admin-dashboard-metrics.ts` と `app/page.tsx` に `ratePercent2` が点在。統一/共通化は将来の掃除対象。

## ADR-008: 管理者はログイン時から管理者画面
- **決定**: `handleLogin` で admin アカウントなら `isAdminMode=true`。
- **背景**: セッションはリロードで消え毎回ログインするため、ログイン処理を直せば毎回管理画面で始まる。
- **影響**: 右下トグルでメンバー画面へ切替は引き続き可能。

## ADR-009: サイドバーUI化（管理者のみ）
- **決定**: 横タブ→左サイドバー、紺ヘッダー廃止・全幅化。メンバー画面は従来のまま。
- **理由**: セクション切替は既に `adminSection` state 管理なので「ガワ」の差し替えで済み低リスク。
- **影響**: スマホはハンバーガーでドロワー開閉。アイコンは依存追加せずインラインSVG(`AdminNavIcon`)。

## ADR-010: Slack日次結果の土日スキップは「対象日ベース」
- **決定**: `slack-report`（深夜0時・前日実績）で、レポート対象日が土日ならスキップ。
- **理由**: 既存 `slack-daily`（朝・稼働予定）と同方式で統一。金曜実績（土曜0時着）は実データなので送る、土日実績（空）は送らない、が自然。
- **影響**: cronはスキップ、手動POST `test:true` は送信可（検証用）。

## ADR-011: 開始打刻なしで終了した時の既定開始時刻は「固定 10:00」
- **決定**: 「開始時間の確認」モーダルの開始時刻の初期表示を `09:00` → `10:00` の**固定値**にする（`app/page.tsx` の `manualStartTimeHhmm` 初期値と、モーダルを開く直前のリセット値の2箇所）。
- **背景**: 実運用の始業が10時で、メンバーが毎回9:00→10:00に直していた（Slackで依頼）。
- **選択肢**: A=固定10:00 / B=その日のシフト予定 `startPlanned` を初期値（無ければ10:00） / C=環境変数で可変。
- **理由**: Aは差分2行で副作用ゼロ。Bは「予定＝実績」になりやすく予実乖離チェックの意味が薄れる。Cは1回きりの変更に対して過剰。
- **影響**: あくまで入力欄の初期値であり、手入力での変更・「現在の時刻を開始とする」の挙動は不変。将来「人により始業が違う」要望が出たらBを再検討する。

## ADR-012: 会社休業日は「期間テーブル＋クライアント側ブロック」・祝日はアプリ内計算
- **日付**: 2026-08-03
- **決定**: ①会社休業日は `company_holidays`（name/start_date/end_date の期間行）で持ち、メンバーのシフト提出UIで土日と同じ「稼働予定なし」固定にする（API/サーバー側の強制はしない）。②休業日の「提案」（GW・お盆・年末年始・平日祝日）は外部APIやライブラリを使わず、`lib/company-holiday-suggestions.ts` で祝日を計算して出す。却下は `company_holiday_suggestion_dismissals` に年別キー（例 `obon-2026`）で記録。
- **背景**: お盆の稼働希望を出せないようにしたいというSlack依頼。年数回の長期休みを毎回手動登録するのは忘れやすいので提案機能も追加。
- **選択肢**: 提案の祝日データは A=アプリ内計算（振替・国民の休日・春分秋分近似式） / B=数年分ハードコード / C=外部API。
- **理由**: Aは新規依存ゼロ・毎年メンテ不要（春分秋分の近似式は2099年まで官報と一致、2026/2027で検証済み）。管理者の代理シフト編集は休業日でも可能のまま（例外対応の裁量を残す・依頼スコープが「メンバーの提出ブロック」のため）。
- **影響**: 祝日法が改正されたら `nationalHolidaysForYear` の修正が必要。休業日の強制はUI層のみなので、APIを直接叩けば理論上は登録可能（既存の土日ブロックと同水準）。お盆=8/13〜8/16・年末年始=12/29〜1/3 は慣習値で、変えたい年は提案を却下して手動登録する。

## ADR-013: 銀行コード・支店コードは全銀協データ内蔵で自動確定（freee連携フェーズ1）
- **日付**: 2026-08-03
- **決定**: freee連携（取引先の振込口座登録）の前提として `users.bank_code / branch_code` を追加。銀行・支店マスタは zengin-code/source-data（MIT・全銀協データ）のスナップショットを `lib/zengin-data.json`（約2MB）としてリポジトリに内蔵し、**サーバー側のみ**で読む（`/api/bank-master` が候補を返し、クライアントには JSON を載せない）。入力 UI は候補選択でコード確定、手入力はコード未確定（空）とする。既存データは管理設定の「一括補完」ボタンで厳格照合（完全一致 or 前方一致1件のみ採用）。
- **選択肢**: A=データ内蔵（採用） / B=外部API（BankcodeJP等） / C=npm パッケージ zengin-code 追加。
- **理由**: Aはランタイム外部依存ゼロ・無料・オフラインで動く。Bは可用性とコスト、Cは依存追加禁止方針に反する。支店統廃合への追従は年1回程度のスナップショット更新で十分（更新手順は lib/bank-master.ts 冒頭コメント）。
- **影響**: マスタが古いと新設・改称支店が候補に出ない（手入力は常に可能・コードのみ未確定になる）。フェーズ2（freee API連携）はこのコードを使って取引先＋振込口座を同期する予定。

## ADR-014: freee API連携はOAuthトークンをservice_role専用テーブルに保管
- **日付**: 2026-08-03
- **決定**: freee会計APIとOAuth2（認可コード）で接続し、トークンは `freee_oauth_tokens`（**RLS有効・ポリシーなし**＝anonキーからアクセス不可、`SUPABASE_SERVICE_ROLE_KEY` 経由のみ）に1行で保管。取引先同期は `users.freee_partner_id` で対応付け、未設定は作成・設定済みは更新。名前重複時はfreee側の同名取引先を検索して自動紐付け。フィールド名はfreee公式OpenAPIスキーマ（freee/freee-api-schema）で確認済み。
- **背景**: 既存テーブルは全てRLS全開放（監査で指摘済み）。freeeのアクセストークンをその流儀で保存するとブラウザから盗めてしまうため、このテーブルだけは閉鎖して唯一の例外パターンとした。
- **選択肢**: A=service_role専用テーブル（採用） / B=Vercel環境変数に保存（refresh_tokenが使い捨てで書き換え必要なため不可） / C=既存流儀のRLS開放（論外）。
- **影響**: 本番の Vercel に `SUPABASE_SERVICE_ROLE_KEY`・`FREEE_CLIENT_ID`・`FREEE_CLIENT_SECRET` が必要。refresh_tokenは使い捨てのため、保存失敗や並行リフレッシュで壊れたら管理設定から「freeeと再接続」で復旧する。事業所は最初の1件を自動採用（複数事業所になったら選択UIを追加）。

## ADR-015: 表示名の正は「姓 名」（半角スペース）・姓名は分離保存（税理士要望による方針転換）
- **日付**: 2026-08-03
- **決定**: 税理士（freee運用者・大槻さん）の要望により、表示名の正規形を「スペースなし」（ADR未記載・第3弾）から「**姓 名**（半角スペース1つ）」へ転換。`users.last_name / first_name` を追加し、姓名確定済みメンバーは `name = 姓 + " " + 名`。書き込み時の正規化は `collapseMemberNameSpaces`（連続空白→半角1つ）、照合は従来どおり `normalizeMemberName`（全空白除去）で不変。
- **背景**: freee取引先マスタの過去運用が「姓 名」区切りで、税理士から姓名分離入力の要請。二重登録はfreee ID紐付けで構造的に発生しない。
- **収集方法**: 既存メンバーの姓名分割データは復元不能（スペース統一時に消失）のため、①本人確認モーダル（姓・名入力を必須表示）②管理者編集（姓・名2欄）で収集。分割未確定の間は name は現状のまま（freeeへの反映も現状名のまま＝退行なし）。
- **影響**: 姓名が確定した人から順に、次回同期でfreee取引先名が「姓 名」へ自動更新される（ID更新のため重複なし）。Googleフォームの名前欄は引き続きフルネーム1欄（スペース入り入力は自動分割・なしはモーダルで収集）。
