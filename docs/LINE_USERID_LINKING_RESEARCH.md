# LINE userId 収集・アプリアカウント紐付け 調査まとめ（2026-08-07）

中野くん知識ループの最終形「Slackの回答をLINEで本人に自動返信（③）」の前提調査。
調査はWeb・LINE公式ドキュメントベース。実装直前に developers.line.biz の最新仕様を再確認すること。

## 結論（推奨）

**個別コード方式**が最も現実的。
メンバーに固有コードをLINEで送ってもらい、Webhook（messageイベント）で `userId` とコードのペアを受けて
Supabase `users` に `line_user_id` を保存する。

- 既存スタック（Next.js/Vercel/Supabase）にAPI Route 1本追加で乗る。新規ライブラリ・LIFF・nonce実装が不要
- 未認証の一般公式アカウントでも使える（友だち一覧API `followers/ids` は認証済み/プレミアム限定なので頼らない）
- メンバーの手間は「コードを1回送るだけ」

## 最重要の事実確認

1. **手動チャットとWebhookは併用できる**（2022-11-30以降）。応答設定で「チャット」ON＋「Webhook」ON。
   メッセージは両方に届くので、**人力チャット運用を壊さずに裏でuserIdだけ回収できる**。
   「応答メッセージ」（LINE標準の自動応答）はOFFにしておく（定型文が先に返ると体験が壊れる）
2. **userIdはプロバイダー単位**。同一プロバイダー配下ならMessaging APIとLINEログイン/LIFFで同じ値
3. **管理画面からは個々のuserIdは見えない**。取得はAPI/Webhook経由のみ
4. **費用**: reply API（返信）は無料・無制限。**プッシュ送信（③の本体）は課金対象**で、
   コミュニケーションプラン(無料)は月200通まで。メンバー数×質問頻度で現行プランの枠を要確認

## 紐付け方式の比較

| 方式 | 実装難度 | 確実性 | メンバーの手間 | 備考 |
|---|---|---|---|---|
| アカウント連携(Account Link) | 高（nonce等） | 高 | 低 | セキュリティ実装必須 |
| LIFF | 高（新チャネル＋前後実装） | 高 | 低〜中 | |
| **個別コード方式（推奨）** | 低〜中 | 中〜高 | 低 | 誤送信リスクは管理画面で取り消せる保険を |
| 手動紐付け | 低 | 低〜中 | なし | 人数が増えると破綻 |

## 実装時の手順（概要）

1. 既存の公式アカウントで Messaging API を有効化（新アカウント不要。アカウントマネージャー→設定→Messaging API）
2. 応答設定: チャットON・WebhookON・応答メッセージOFF
3. Webhook URL に Vercel の API Route（例 `/api/webhooks/line-userid`）を設定
4. `users` に `line_user_id` カラム追加＋個別コードの発番
5. メンバーへ「このコードをLINEに送ってください」と周知 → Webhookで突合して保存 → reply APIで「登録できました」（無料）
6. 管理画面に連携状況一覧（連携済み/未連携、疑わしい紐付けの取り消し）

## 落とし穴

- `followers/ids` API は未認証アカウントでは使えない（前提にしない）
- プロフィールAPIはユーザーの同意がないと失敗することがある
- コード方式はなりすましがゼロではない → Webhookログを管理画面で見られるようにし、手動取り消しを用意
- プッシュ課金は月間通数を見てプラン判断
