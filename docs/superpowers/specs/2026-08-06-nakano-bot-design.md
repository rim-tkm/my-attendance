# AIアシスタント「中野くん」 設計書

- 作成日: 2026-08-06
- ステータス: 承認済み（実装計画へ）

## 1. 目的

公式LINEに来ているメンバーからの質問を、アプリ内に集約する。
管理者（作業者）がLINEで1件ずつ手で返している状態をなくし、
定型的な質問はAIが即答し、人が判断すべきものだけをSlackに流す。

副次的に、**届いた質問がすべてログに残る**ため、
「何が分かりにくいか」がデータとして見えるようになる。

## 2. 前提と背景

- LINEに来る質問は4種類: 操作方法・ルール／自分のデータの確認／トラブル報告／営業・業務の相談
- マニュアル・ルールの文書は既に存在する（外部ドキュメント）
- 公式LINEを有料プランにするとチャット履歴をダウンロードでき、
  **実際の質問と回答のペア**が取れる。これが知識の初期投入源になる
- LINE自体は廃止しない。押し忘れロック解除の申請など、LINE前提の運用が残る

## 3. スコープ

### やること（第1版）

- マニュアル／FAQの範囲で質問に答えるチャットボット
- 答えられない質問を Slack に自動通知して人につなぐ
- 管理画面から知識を追加・編集できる
- 届いた質問のログを管理画面で閲覧できる
- 概算費用を管理画面で確認できる

### やらないこと（意図的な見送り）

| 見送るもの | 理由 |
|---|---|
| 本人の稼働・KPIデータの参照 | 金額・実績の誤回答は影響が大きい。1ヶ月運用してから判断する |
| ベクトル検索（RAG） | 現在の文書量なら全文を context に載せられる。ライブラリ追加に見合わない |
| LINE API との自動連携 | 別プロジェクト。今回は履歴を人手で取り込むのみ |
| 管理者向けの集計質問 | メンバー向けが安定してから |

## 4. データモデル

新規テーブル3つ。すべて `ENABLE ROW LEVEL SECURITY` かつ **ポリシーを作らない**
（anon キーからは一切アクセス不可、サーバーの service_role 経由のみ）。
`users` の RLS 締め（2026-08-05）および `announcements`（2026-08-05）と同じ方針。

### `nakano_knowledge` — 中野くんの知識

短い一問一答も長文のルール説明も、同じ「タイトル＋本文」で表現する。
1テーブルにまとめることで管理画面が1つで済む。

| 列 | 型 | 説明 |
|---|---|---|
| `id` | UUID PK | |
| `title` | TEXT NOT NULL | 何についての項目か（例:「シフトの提出期限」）。ステップUIではボタンの文言になる |
| `body` | TEXT NOT NULL | 中身。そのままモデルに渡る／ステップUIではそのまま回答として表示される |
| `category` | TEXT NOT NULL DEFAULT 'other' | `operation` / `rule` / `billing` / `other` |
| `parent_id` | UUID REFERENCES nakano_knowledge(id) ON DELETE CASCADE | ステップUIの親。NULL なら最上段 |
| `show_as_step` | BOOLEAN NOT NULL DEFAULT false | true ならステップUIのボタンとして出す（§5-B） |
| `is_active` | BOOLEAN NOT NULL DEFAULT true | false にすると中野くんが参照しなくなる（削除せず一時停止） |
| `sort_order` | INTEGER NOT NULL DEFAULT 0 | 並び順 |
| `created_at` / `updated_at` | TIMESTAMPTZ | |

インデックス: `(is_active, sort_order)`、`(parent_id, sort_order)`

**1レコードが2つの役割を兼ねる。** 同じ行が、ステップUIのボタン＋回答としても、
AIに渡す知識としても使われる。二重管理を避けるための設計。

### `nakano_conversations` — 会話のまとまり

| 列 | 型 | 説明 |
|---|---|---|
| `id` | UUID PK | |
| `user_id` | UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE | |
| `created_at` / `updated_at` | TIMESTAMPTZ | |

インデックス: `(user_id, updated_at DESC)`

**会話の切り替わり規則:** パネルを開いたとき、そのメンバーの最新の会話の
`updated_at` が24時間以内なら継続、それより古ければ新しい会話を作る。
別の日の質問が同じスレッドに繋がって文脈が混ざるのを防ぐため。

### `nakano_messages` — 1つ1つの発言

| 列 | 型 | 説明 |
|---|---|---|
| `id` | UUID PK | |
| `conversation_id` | UUID NOT NULL REFERENCES nakano_conversations(id) ON DELETE CASCADE | |
| `user_id` | UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE | 回数制限の集計をJOINなしで行うための非正規化 |
| `role` | TEXT NOT NULL CHECK (role IN ('user','assistant')) | |
| `content` | TEXT NOT NULL | |
| `source` | TEXT NOT NULL DEFAULT 'ai' CHECK (source IN ('ai','step')) | `step` はステップUIの操作（API未使用・課金なし） |
| `escalated` | BOOLEAN NOT NULL DEFAULT false | この回答で担当に回したか |
| `input_tokens` / `output_tokens` | INTEGER | assistant かつ `source='ai'` のみ。費用集計用 |
| `created_at` | TIMESTAMPTZ | |

インデックス: `(conversation_id, created_at)`、`(created_at DESC)`（管理画面の新着順用）、
回数制限用に `(user_id, source, role, created_at DESC)`。

**回数制限は専用テーブルを持たない。**
`nakano_messages` の `user_id` / `role='user'` / `source='ai'` / `created_at` で数える。

## 5-A. 利用条件（誰が・いつ・何回まで）

AIへの質問は無制限に開けない。人数が増えると費用が線形に増え、
「AIだから何でも聞ける」という使われ方をすると本来の目的（稼働中の困りごと解決）から外れるため。

### 対象者

| 区分 | 中野くん |
|---|---|
| 業務委託（時給制メンバー） | **使える** |
| インターン（`isIntern=true`） | **表示しない。** シフトが無く時間帯判定ができないため。質問は従来どおりLINEで受ける |
| 管理者（`loginAccount === "admin"`） | 常時使える（試運転・運用確認のため） |

### 時間帯

**当日の提出済みシフトの、予定開始30分前〜予定終了30分後**の間だけ。
2部（`startPlanned2` / `endPlanned2`）がある場合はその区間も対象に含める（2区間の和集合）。

- 実際の打刻状態ではなく**シフト予定**で判定する。
  「稼働開始ボタンが押せない」という最も多い相談を、押す前に受けられるようにするため。
  また、稼働終了を押し忘れても予定終了+30分で自然に閉じる。
- シフト未提出の日・範囲外の時刻は「稼働時間外です。急ぎなら公式LINEへ」。

**ただしステップ式クイック回答（§5-B）は時間帯の制限を受けない。**
APIを呼ばず費用が発生しないうえ、稼働時間外にルールを確認したい場面は正当なため。
時間帯で閉じるのは自由入力によるAIへの質問だけ。

### 回数

| 制限 | 既定 | 環境変数 |
|---|---|---|
| 直近60分あたり | 5問 | `NAKANO_HOURLY_LIMIT` |
| 1日（JST）あたり | 15問 | `NAKANO_DAILY_LIMIT` |

- 数えるのは `source='ai'` かつ `role='user'` のメッセージのみ。
  **ステップ式クイック回答の操作はカウントしない。**
- 60分は暦の「毎時0分区切り」ではなく直近60分のローリング判定。
  区切りの直前直後に連投して2倍撃てる穴を塞ぐため。
- 上限に達したら、次に空くおおよその時刻とLINE導線を返す。

これらの判定はすべて**サーバー側（`/api/nakano/chat`）で行う**。
画面でボタンを隠すだけでは、APIを直接叩けば通ってしまうため。

## 5-B. ステップ式クイック回答（API未使用）

パネルを開いた直後に出るのは、自由入力欄ではなく**よくある質問のボタン**。
ここで解決すればAPIを一度も呼ばない。費用が下がり、即答なので体感も速くなる。

```
[パネルを開く]
   ↓
よくある質問のボタンが並ぶ（nakano_knowledge の show_as_step=true, parent_id IS NULL）
   ↓ 押す
本文を表示し、子があればさらにボタンを並べる（何段でも可）
   ↓ 末端まで来た
「解決しました」／「解決しなかった・別のことを聞く」
   ↓ 後者を押す or 自由入力
ここで初めて Claude を呼ぶ（回数制限・時間帯制限の対象）
```

- ステップの内容は `/api/nakano/steps` で**一度だけまとめて取得**し、
  以降のボタン遷移はサーバー往復なしで動く。全メンバー共通の内容なので個別化は不要
- 返すのは `show_as_step=true` の行だけ。AI専用の知識は返さない
- ステップの操作も `nakano_messages` に `source='step'` で残す。
  **どのステップまで進んで解決しなかったかが、FAQ改善の一番の材料になる**ため

## 5-C. 回答の組み立て（AIを呼ぶ場合）

### システムプロンプトの構成

以下を連結して `system` に渡す。順序は固定（プロンプトキャッシュのため）。

1. **役割** — 株式会社RIMの業務委託・インターン向けアシスタント「中野くん」
2. **口調** — LINE履歴から抽出した実際の返し方
3. **ガードレール**
   - 渡された知識に書いていないことは推測で答えない。分からないと言う
   - 次の話題は答えずに担当へ回す:
     **報酬額／契約条件／契約解除／他人の情報／体調・人間関係の相談**
   - 個人の稼働時間・KPIの数値は答えない。画面上の場所を案内する
   - AIであることを隠さない
4. **知識** — `nakano_knowledge` の `is_active=true` を `sort_order` 順に全件

3までは固定文字列（`lib/nakano-prompt.ts`）、4はDBから組み立てる。

### モデル設定

| 項目 | 値 | 理由 |
|---|---|---|
| モデル | `claude-opus-5`（`NAKANO_MODEL` で変更可） | ガードレール遵守の精度がそのまま誤回答リスクに直結する。実ログを見てから下げられるよう環境変数化 |
| thinking | `{ type: "adaptive" }`（既定） | 明示的に無効化するとツール呼び出しが本文テキストに混ざる不具合があるため無効化しない |
| effort | `low` | FAQ検索的な単純タスク。判定が甘ければ `medium` に上げる |
| max_tokens | 4000 | thinking を含む上限 |
| ストリーミング | 有効 | 数秒の無反応で「壊れた」と判断されるのを防ぐ |
| プロンプトキャッシュ | 知識ブロックの末尾に `cache_control: { type: "ephemeral", ttl: "1h" }` | 入力コストを約1/10に。知識を編集すると自然に新しいキャッシュへ切り替わる |

会話の文脈は、同一 conversation の直近メッセージを `messages` に載せて渡す
（上限は直近20件。それ以上は古い順に落とす）。

### エスカレーション判定

キーワード一致ではなく、**モデルにツールを1つ渡して判断させる**。
「解約／辞めたい／やめる」のような言い換えを人手で列挙するのは不可能なため。

```
tool: escalate_to_admin
  input_schema:
    reason: string   // なぜ人に回すのか（Slackに載せる）
    summary: string  // 質問の要約
```

モデルは「すみません、これは担当に確認しますね」という本文を書きつつ
同じターンでこのツールを呼べる。ツール呼び出しを検出したら:

1. Slack（用途 `nakano`）へ メンバー名・質問・reason を通知
2. その assistant メッセージの `escalated` を true で保存
3. メンバー側の吹き出し下に「担当に届けました」を表示

ツールの実行結果はモデルに返さない（1往復で完結。ツールランナーは使わない）。

## 6. API

すべて `getServerSession(authOptions)` で認証。ログイン必須。

| ルート | メソッド | 役割 |
|---|---|---|
| `/api/nakano/status` | GET | 表示してよいかだけを返す軽い問い合わせ。**知識0件・テーブル未作成はすべて `ready:false` を200で返す**（未使用のメンバーの画面にエラーを出さないため） |
| `/api/nakano/chat` | POST | 質問を受け、回答を NDJSON でストリーム返却。対象者・時間帯・回数を検証 |
| `/api/nakano/steps` | GET | ステップ式クイック回答のツリー（`show_as_step=true` のみ）を一括返却 |
| `/api/nakano/step-log` | POST | ステップ操作の記録（`source='step'`）。回数制限の対象外 |
| `/api/nakano/conversation` | GET | 自分の直近の会話と発言、および現在の利用可否（時間帯・残り回数）を返す |
| `/api/admin/nakano/knowledge` | GET / POST | 知識の一覧・追加 |
| `/api/admin/nakano/knowledge/[id]` | POST | 知識の更新（`is_active` の切替を含む） |
| `/api/admin/nakano/logs` | GET | 会話ログ一覧（新しい順・ページング） |
| `/api/admin/nakano/usage` | GET | 当月の質問件数とトークン合計 |

`/api/admin/*` は `session.user.loginId === "admin"` を確認する（既存の管理APIと同じ）。

### `/api/nakano/chat` のレスポンス形式

行区切りJSON（NDJSON）。1行1イベント。

```
{"type":"text","text":"シフトの提出期限は"}
{"type":"text","text":"毎週木曜23:59です。"}
{"type":"escalated"}
{"type":"done"}
{"type":"error","message":"今つながりません。急ぎなら公式LINEへ。"}
```

## 7. メンバー側UI

### フロートボタン

- 全画面の**左下**に固定。インラインSVGのアイコン（新規ライブラリなし）。
  右下はログアウトボタンと重なるため（2026-08-06の実機確認で判明）
- 管理画面表示中は出さない
- **インターンには出さない**
- 未読の担当回答があっても通知バッジは出さない（第1版では回答はLINE/口頭で返るため）

### チャットパネル

- 押すと左下から立ち上がる。モバイル幅では全画面
- ヘッダー: 「中野くん」＋ `AI` バッジ
- 初回のみ上部に注意書き:
  > 中野くんはAIです。間違えることもあります。
  > **報酬・契約に関することは、必ず担当に直接聞いてください。**
- **ステップ式のボタンは会話の下・入力欄の上に固定**し、開いてもそこだけがスクロールする。
  会話と同じスクロール領域に置くと、項目数が多いぶん回答が画面外へ押し上げられる（実機確認で判明）。
  自由入力で質問を送った時点で自動的に畳み、回答の表示領域を広げる
- 過去のやりとりはDBから復元して表示
- 回答は1文字ずつ流れて表示
- 担当に回されたメッセージには `担当に届けました` を表示
- 稼働時間外／回数上限に達しているときは、自由入力欄を無効化して理由とLINE導線を出す。
  ステップ式のボタンは引き続き使える

## 8. 管理画面

`AdminSection` に `"nakano"` を追加。
CLAUDE.md §5 のとおり「型 → `navItems` → `AdminNavIcon` → 描画ブロック」の4点セットを揃える。

| カード | 内容 |
|---|---|
| 知識の管理 | 一覧・追加・編集・有効/無効の切替 |
| 届いた質問 | 新しい順。メンバー名・日時・やりとり・エスカレーション印。**FAQを育てる起点** |
| 今月の使用状況 | 質問件数とトークン数からの概算費用。モデル変更の判断材料 |

## 9. 上限・エラー時の動き

| 状況 | メンバーに見えるもの | 付随処理 |
|---|---|---|
| 稼働時間外（シフト予定±30分の外） | 「今は稼働時間外です。よくある質問は見られます。急ぎなら公式LINEへ」 | ステップ式は使える |
| 直近60分の上限（既定5問）超過 | 「少し間を空けてください。◯時◯分ごろにまた聞けます」 | ステップ式は使える |
| 1日の上限（既定15問）超過 | 「今日はここまでです。急ぎなら公式LINEへ」 | ステップ式は使える |
| Anthropic API 障害 / キー未設定 | 「今つながりません。急ぎなら公式LINEへ」 | Slack に障害通知 |
| 知識が0件・テーブル未作成 | **何も表示されない**（フロートボタンごと出ない） | — |

**どの失敗経路でも必ず公式LINEという逃げ道を提示する。**
中野くんが黙って壊れ、メンバーが誰にも聞けなくなるのが最悪のケースであるため。

## 10. 環境変数

| 変数 | 既定 | 用途 |
|---|---|---|
| `ANTHROPIC_API_KEY` | なし（必須） | 未設定なら中野くんは常にエラー応答 |
| `NAKANO_MODEL` | `claude-opus-5` | モデル切替 |
| `NAKANO_DAILY_LIMIT` | `15` | 1人1日あたりのAI質問上限 |
| `NAKANO_HOURLY_LIMIT` | `5` | 1人・直近60分あたりのAI質問上限 |
| `NAKANO_SHIFT_MARGIN_MINUTES` | `30` | シフト予定の前後マージン |
| `SLACK_WEBHOOK_NAKANO_URL` | 既定の `SLACK_WEBHOOK_URL` | エスカレーション通知先 |

`lib/slack-webhook.ts` の `SlackWebhookPurpose` に `"nakano"` を追加する。

## 11. 依存の追加

`@anthropic-ai/sdk`（Anthropic公式）を1つだけ追加する。
CLAUDE.md §6「新規ライブラリは原則追加しない」に対する明示的な例外。

理由: 自前の `fetch` でClaudeを呼ぶと、SSEのパース・リトライ・エラー分類・
トークン集計・プロンプトキャッシュのヘッダ管理をすべて自作することになり、
公式SDKを入れるより保守負担が大きい。

UIライブラリは追加しない（アイコンはインラインSVG、見た目は既存のTailwindトークンを踏襲）。

## 12. 費用の見積もり

前提: 知識8,000トークン、回答350トークン、思考込みで出力1.4倍、1ドル155円、
1時間TTLのプロンプトキャッシュを利用、営業日22日/月。

| 1日の質問数 | Opus 5 | Sonnet 5 | Haiku 4.5 |
|---|---|---|---|
| 30件 | 約6,000円/月 | 約3,600円/月 | 約1,200円/月 |
| 100件 | 約11,000円/月 | 約6,800円/月 | 約2,200円/月 |
| 300件 | 約27,000円/月 | 約16,000円/月 | 約5,200円/月 |

**この表はステップ式クイック回答を考慮していない上限値。**
よくある質問の相当部分がステップ側で解決すればAPI呼び出しはその分減るため、
実際の請求はこれより低くなる見込み。どれだけ減るかは運用ログで測る。

暴走対策は4段構え:
1. Anthropic Console 側で月額の上限を設定
2. ステップ式クイック回答で、そもそもAPIを呼ばずに済ませる
3. 1人・直近60分あたりの上限（`NAKANO_HOURLY_LIMIT`）
4. 1人・1日あたりの上限（`NAKANO_DAILY_LIMIT`）＋稼働時間帯の限定

## 13. 実装の順序

1〜3は**LINE履歴を待たずに進められる**。箱を先に作り、届いたら中身を入れる。

1. 土台 — SQL、`lib/nakano-*.ts`（利用可否・回数・ステップ木の組み立て）、Anthropic SDK追加
2. API — `/api/nakano/{chat,steps,step-log,conversation}`
3. メンバー画面 — フロートボタン、ステップ式ボタン、チャットパネル、ストリーム表示
4. 管理画面 — 知識管理（階層編集を含む）・会話ログ・使用状況の3カード、Slack通知
5. 中身の投入 — LINE履歴とマニュアルから知識とステップの初版を作成（**履歴の到着待ち**）
6. 試運転 — 管理者と実際に質問を投げ、誤りを知識で修正
7. 公開 — メンバーに開放

## 14. 検証方法

このリポジトリにテストフレームワークは無い。品質ゲートは以下:

- `npx tsc --noEmit` と `npm run build`（両方必須）
- 純粋ロジック（知識の組み立て・**利用可否判定**・**回数制限**・ステップ木の組み立て・
  NDJSONの整形）は `npx tsx` の検証スクリプトで確認する（scratchpad、リポジトリには含めない）。
  特に時間帯判定は、シフト無し／1部のみ／2部あり／境界ちょうど／日跨ぎ の各ケースを確認する
- 実挙動は `npm run dev` で実際に質問を投げて確認する
- ガードレールの確認は必須。少なくとも次の4つを手で試す:
  - 知識に無い質問 → 推測で答えず、担当に回されるか
  - 「報酬いくらですか」 → 答えずに担当へ回るか
  - 「今月の稼働時間は」 → 数値を答えず画面を案内するか
  - 上限超過・稼働時間外 → LINEへの導線が出て、ステップ式は使えるか
  - インターンのアカウントでボタンが出ないこと、かつAPIを直接叩いても拒否されること
